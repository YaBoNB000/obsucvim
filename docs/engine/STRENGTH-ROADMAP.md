# 混淆强度提升路线图（STRENGTH-ROADMAP）

> 立项依据：2026-10-25 用户提出「混淆强度不知道怎么提升」。本文是**重新开工前的规划文档**，
> 不是执行记录。现状基线见 [`../CURRENT-STATE.md`](../CURRENT-STATE.md)，逐轮证据见
> [`ENGINE-VERSION.md`](ENGINE-VERSION.md)。

---

## 1. 结论先行

强度的下一个台阶**不在「再加一层随机化」**，而在三件事：

1. **先有可度量的强度判据**——仓库至今没有静态拆包回归器，所以「强度有没有提升」无法回答，
   这正是「不知道怎么提升」的根因。
2. **最高价值的引擎项是 R2 执行门控**（装载期不再解出全量密钥流），其次是
   **bx 车道重做非线性折叠**（唯一还留在「已知一处明文即可推整条流」的密码学缺口）。
3. **当前最大的实际强度缺口在交付侧而非引擎**：控制台默认走 `safe`（`--no-bind-executor`），
   绝大多数成品拿不到 executor 绑定与环境检查这两层。

## 3. 三类杠杆与优先级

| 类别 | 代表项 | 收益性质 | 成本 | 排期 |
| --- | --- | --- | --- | --- |
| 存在性（能不能静态解出） | R2 执行门控（G3） | **跳变**：静态与半动态同时失效 | 3–4 轮 + 判别件 | R3 |
| 密码学（解出来要多久） | bx 车道 NL 重做（G2）、CLK 真混入（G4） | 线性→非线性，消灭单点明文推全流 | 1–3 轮 | R1–R2 |
| 纹理/成本（每样本人工费） | R6 续、P5 `--super-insn` 翻默认（G6 顺带） | 边际递减 | 1–2 轮 | R4 |

排序原则：**先能度量（G1）→ 先修「宣称与事实不符」（G4/G5）→ 再动最高价值但高风险的
（G2 → G3）→ 最后才是纹理。**

## 4. 路线图（每轮独立可交付、独立验收）

### R0｜工具链恢复 + 强度判据（前置，无引擎语义变更）

- 用 npm `@rustbin`（`rustc-1.88.0` + `rust-std-1.88.0-wasm32-wasip1` + `cargo`）重建 `.tools`，
  按 `engine/tools/rebuild_tools.sh` 装回 `lua51`/`luau`/`luau-compile`。
  （已验证包在 registry 上可取：`@rustbin/rustc-1.88.0-…` = 1.88.0、`rust-std-…-wasm32-wasip1` = 1.88.0。）
- 从源码重编 wasm，**冲销「R077 + 数据段手术」的发布债**：源码已是 R079，正牌重编后
  锚点必须仍是 178,551 B / `ccf5d083…`；不等即说明手术件与源码不同义，必须先对齐。
- **交付 `web/tools/test-static-unpack.py`**：按 V19 §4 口径实现常折器 + 钥链提取 +
  段解密 + 校验复算，判定「不引入运行时值时能否解出任一段明文」，扫描 ≥4 种子 × on/off。
  产出**基线分数**（当前 R079 的可静态解出比例）——这是后续每轮的统一记分板。
- 验收：单测/六套件恢复可跑；锚点复现；基线分数入库（写入本文 §6）。

### R1｜CLK 真接入 + P3 镜像审计（低成本确定性收益）

- 把 `CLK`/`PCAL` 接进 EP build chunk 签名，让时钟采样**真正进入钥流**（G4），
  同时保证同构建逐字节确定（时钟只在运行时采样一次，编译期不参与；镜面用幂二次整除）。
- 对 G5 做静态定向审计：确认 mu/mnp 不对称是「漏」还是「设计」；是漏则修，是设计则加注。
- 风险：时钟入流会引入运行期不确定性 ⇒ 必须先立判别件（见 §5），且失败形态必须是
  fail-fast 而非静默挂死。
- 验收：静态拆包基线分数不降；真机双件正常。

### R2｜bx 车道非线性重做（G2，密码学级）

- R077 的教训：三车道同时上 NL 且一次上两级折叠，判别只能事后三分。本轮改为
  **单车道、单级、带判别件**推进：先换 fold 式（避开已知失步形态），单级上，真机过，
  再叠第二级。
- 复用法：`artifacts/samples/obsucvim/v19-check/diff-flight/` 的 F/L 判别链（F1/F2 分级、
  L1–L3 分车道）已跑通三轮，直接复用。
- 收益：消灭「单点已知明文 ⇒ SALT ⇒ 整条字节流」，使 L1/L3 失守主路径不再线性可延展。
- 验收：静态拆包基线分数**显著下降**（量化）；判别件真机通过；`--no-bind` 矩阵逐字节恒等。

### R3｜R2 执行门控原型（G3，存在性级，最高价值）

- 落点已定：stage-2 `bdec` 懒解层（§7.4）。子函数段钥 = 父闭包**编译期可证无缝**直线前缀的
  dispatch 折叠 + EV；只装载不执行 ⇒ 段钥信息论缺失。
- 先做原型自洽性矩阵（不改交付形态），验证「检查点前缀可证性分析」能覆盖语料的多少比例；
  覆盖不足则退化为「函数粒度确定性检查点」（§7.4 既定备案）。
- 风险：会动到 bdec 键源与编译器前缀分析，是全仓库最难的一块；必须独立判别件 + 可回退开关。
- 验收：静态拆包对子函数段**完全解不出**；运行等价矩阵全绿；真机双件正常。

### R4｜纹理收官 + 卫生（可选，边际）

- P5：Phase-1c 窗口 3 + `--super-insn` 翻默认（VM 指令面）。
- 修 `--no-minify` 调试通道失真（G6），避免后续调试踩空。
- 收益有限，仅在前四轮完成后做。

### 并行（不等引擎，今天就能提升交付强度）

| 动作 | 影响 |
| --- | --- |
| 交付默认切 `hard`（`--env-check --bind-executor`），`safe` 仅作 fallback | 最大实际缺口：目前默认 `safe`（`web/src/lib/engine.ts` `hardening:false`） |
| MW-1 默认开启（`--num-fog 0.55 --blocks 6`） | 源级不透明门 + 字面量恒等链，体积 +25~30 KB |
| 每客户唯一 seed + 双产物隔离 | 防跨客户样本互推（同 seed 同形态会互相泄露） |
| 禁交付 `Off`/`Dev`/`no-minify` 件 | 文档已明示，需在执行侧硬拦 |

## 5. 每轮固定门禁（缺一不算完成）

1. 单测绿（当前 61）；`cargo build --release` 无新告警。
2. no-bind 矩阵：auto/off/DEV 逐字节恒等；四件 luau 实跑输出恒等。
3. 多种子回归 0 失败（≥5 seed × 全语料）。
4. 六套件全绿（hosting/loader/attest/live-loader/artifact-runtime/exguard-precheck）。
5. **静态拆包回归**：基线分数不得回升（红 = 失守）。
6. **真机双件**：新锚点出 evkey + ctl 双件，真 Delta 回传「正常」才算收口；
   异常先出判别件（分级/分车道），不猜。

## 7. 需要拍板的 3 件事

1. **是否解除 §34 收摊令**（限定范围：只做 §4 的 R0–R4 强度项，不动发布管线）。
   收摊令原文见 `ENGINE-VERSION` §13/§34；不解除则本路线图不启动。
2. **交付默认是否切 `hard`**：取决于目标执行器覆盖率（`hard` 在缺 API 的环境里
   fail-fast 拒绝执行，虽是既有文案但仍会掉用户）。
3. **可接受的迭代节奏**：R0 一轮即可出基线；R1 一轮；R2 两到三轮；R3 三到四轮
   （含原型）。若只给 2–3 轮预算，建议 **R0 + R1**（先可度量 + 兑现宣称），
   R2/R3 另批。
