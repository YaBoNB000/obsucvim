## 特别澄清现有文档中的过强表述

旧文档个别地方说 “SALT 每运行必变 ⇒ 快照重放已免疫” 或 “静态文件没有运行盐 ⇒ 不存在离线解码器”。这些不是普适的密码学论证。本轮不修改历史文件，但研究结论不沿用这类绝对措辞：

- 表/闭包地址、时钟是运行态数据，不是保证保密的信任根，也没有保证跨次不重复。
- 完整状态快照包括盐和解码状态；同进程观察者能同时获取密文与使用它的状态。
- 旧密钥配新密文失效，不能推出旧密文配旧密钥无法离线分析。
- 确定性演进可增加同步负担，但拿到当前状态的一方通常仍可向前计算；完整回滚则会把检查状态一起回滚。
- 只读观察若不改变程序可见状态，离线程序内部没有通用判据能区分它与干净运行。

## C4 的新实验及局限

`reseal.luau` 仅模拟 session blob 旋转，**不是复制/修改现役 codec**：

1. 先确认旋转前后内容解码一致。
2. 正面例：旧 key 解新 blob 错误。
3. 反例：已知演进规则可推新 key；8-bit 掩码 256 次循环；完整快照仍能解出全部记录。
4. 交错模型：多 record 懒读跨用户回调发生重入重密封时可能混用 generation。当前 R064 单 record recipes 已缩小这一风险，模型反例不能直接当作现役 bug。
5. 提前全部物化可避免该交错，但会延长完整明文 record 在用户回调期间的驻留窗口。
6. 全 shard immutable string 重写是 O(shard bytes)；切到 per-record buffer/状态表可能降低成本，但增加枚举边界/索引/密钥状态，未做正式实现，也未证明不会重开 H5-P0 问题。

不把简单模 256 旋转包装成密码学 ratchet，也不把此模型的性能倍数套到完整 VM。
