## 3. C1：一次消费、帧所有权、阶段绑定的调用完成凭证

### 为什么在当前仓库算不同的候选

现有 `CALL → CX → POSTCALL` 已分相、按 call-family 使用不同数字槽。候选试图增加的是：每次实际调用的完成事件只能归还给它所属的帧、所属阶段，而且只能消费一次。它不是把 H4-6B 的块解码 epoch 改名。

### 能验证的收益

独立 Python 模型 20,000 轮、8 帧随机完成顺序：

- 160,000 次合法完成通过；
- 160,000 次跨帧错投被拒绝；
- 160,000 次重复消费被拒绝；
- 160,000 次错误阶段被拒绝。

**这些数字只属于协议模型，不代表对正式 VM 做了 160,000 次攻击。**

### 已证伪的强承诺

同一模型中：

- 当前合法凭证被同进程观察者拿走后，可不执行预期计算而提交：20,000/20,000 接受。
- 把全部验证状态一同恢复后再次提交：20,000/20,000 接受。

因此它只能提高有限的错投/旧事件重放成本，不能证明“调用确实按原语义执行”，也不检测只读调试器。

### Luau 正向测试

`behavior.luau` 实测通过：尾 nil 和返回数量、零返回、单 nil、错误对象身份、nil 错误对象、40 层递归重入、16 协程交错共 512 次 yield、受保护 `__call` 元方法仅执行一次。

### 必须淘汰的外层 wrapper 形态

复现了以下合法语义改变：

1. 程序用 `debug.info(2, "f")` 判断立即调用者，未包装时正确，包装后错误。
2. `error(..., 2)` 错误位置改变；本地反例中原本携带调用位置的错误变为无该位置的消息。
3. 全局单一 pending 标记会把另一个正常协程误认为重入攻击。
4. `coroutine.close` 取消 suspended 调用时，返回后的清理语句不会执行。若把 pending 存在强引用全局注册表，会产生清理/驻留风险；本实验没有声称测量了真实堆泄漏。

9 轮交错顺序微基准，每轮 50,000 调用，候选相对于**同样 pack/pcall 的无凭证 adapter**中位耗时约 **1.703×**。这不是完整 VM 的开销；也没有测量全部内存/GC 影响。

**结论：外层统一 wrapper 方案淘汰。** 只有“在现有分散 CALL/POSTCALL 位置内联、保持原调用栈、无新增中央验证函数/全局 registry”的版本值得继续设计；该版本尚未实现，不能拿外层测试为它背书。

## 4. C2：实际控制流边的见证

### 独立状态机结果

模型维护独立预期 PC/序号和合法后继集合，随机合法路径合计 279,535 次迁移均通过；同数量非法边与重复事件被拒绝。

同时复现三类局限：

- CFG 允许的两个后继中，攻击者选了与真实条件不符的那个，CFG-only 检查仍会通过。
- 从当前（已被改写的）PC 算标签，再用同一个 PC 复算标签，是自证循环，不提供独立约束。
- `tag = a*x + y mod 2^32` 可通过补偿改动构造碰撞；20,000 组反例全部成功。这不是密码学 MAC。

### 退步风险

显式合法边表可能向分析者直接暴露 CFG；统一 `verify_edge` 可能变成比现有多 shard 更好下手的单一钩点。重复计算分支条件还可能二次触发用户函数/元方法。

**结论：不推荐简单 CFG 表 + 中央 checker，也不推荐线性标签包装。** 如继续，需在原 handler 语义内一次求值、分散推进、无可枚举全局图；必须分别验证分支条件完整性与边合法性，不能混为一谈。当前仅为设计约束，无不倒退证明。

## 5. C3：算术冗余、双轨运算、数值见证

### 精度试验

- Python 20,000 组随机 32-bit 乘法：用 double 先乘再 mod 2^32，19,298 组与精确整数结果不一致。
- 真 Luau 10,000 组、对照 bit32 逐位乘法：朴素 double 算法 9,754 组不一致。
- 把乘法拆为 16-bit limbs、使每个中间值落在 double 精确整数范围，两组测试均 0 不一致；有代数范围依据，不仅是样本碰巧正确。

这个反例**不是证明现役模运算有错**。现役许多计算已限制操作数范围，本实验针对的是候选新公式可否随意使用 32×32-bit 乘法。

### 合法数值/副作用反例

- `NaN == NaN` 为 false，不能用“与自身相等”当通用完整性约束。
- `inf - inf` 是 NaN，不是 0。
- `(2^53 + 1) - 1` 不等于原值。
- 为比对而重复用户加法会二次执行 `__add`；即便两次结果相同，副作用次数也已改变。

**结论：通用用户运算双执行方案淘汰。** 私有、纯整数、已证明范围的检查可做正确性辅助，但这本身不是新的强反调试层。

## 6. C4：micro descriptor 消费后重密封

### 与已有机制的区别

现有 H5-P0 在启动期把 descriptor carrier 转成 session blob；之后使用时按 session mask/step 解码。候选是每次消费后让该密文继续变化，不等于已有的 block 窗口重掩码。

### 独立模型结果

`reseal.luau` 验证旋转不会破坏解码，同时复现：

- 旧 key 配新 blob 失败；**但是**已知更新公式可算出下一 key。
- 8-bit 掩码 256 次后循环；这只说明朴素模型，不能推断更宽状态也只有 256 次。
- 完整密文+状态快照仍能恢复全部记录；密文在动不等于攻击者无法跟着动。
- 多 record 懒读在用户回调重入时可能混用 generation；当前 R064 单 record recipes 降低了这一场景风险，因此**不把该模型反例当作现役 bug**。
- 预先全读可避免交错，但会把完整明文记录留过用户回调，改变原有观察窗口。

### 资源代价

不可变字符串按全 shard 重密封，1,000 次读取的模型对照：

| 模型 blob 大小 | 固定掩码四字节读取 | 每次读后重写整 blob | 相对倍数 |
|---|---:|---:|---:|
| 4 KiB | 0.000272 s | 0.413244 s | 约 1,520× |
| 16 KiB | 0.000249 s | 1.696971 s | 约 6,811× |

基线非常短，倍数受噪声影响；这是**单次模型测量**，不是完整 VM benchmark。可以确认的是复杂度差异：原来只解当前记录，现在每次复制全部 blob。把它改成 per-record mutable buffer 会换来不同的状态表/边界/原语暴露面，尚未实现和验证。

**结论：当前朴素形态淘汰。** 不因增加 epoch 就宣称前向保密、快照免疫或反 debugger。

## 7. 本轮意外发现：现役随机 seed 多返回值差异

### 原始复现

```bash
engine/target/release/obsucvim --seed 10770986916448599986 \
  engine/tests/cases/stress_multival.lua /tmp/stress-target.lua
.tools/bin/luau engine/tests/cases/stress_multival.lua
.tools/bin/luau /tmp/stress-target.lua
```

源语料：`fwd1: 1 2 3`；现役 v15 产物：`fwd1: 1 9 3`。两者退出码均为 0，属于静默语义差异。

同一产物每种模式跑十次：

| 模式 | 与源码不同 |
|---|---:|
| 默认 v15 | 10/10 |
| v15 `--no-minify` | 10/10 |
| v15 `--no-vm-seal-strings` | 10/10 |
| legacy `--preset vm` | 0/10 |
| `--preset low` | 0/10 |

这些开关改变了多处生成/布局因素，结果只能帮助划定排查范围，**不足以直接归因到某个模块**。

`reproduce_baseline.py` 做 107 次删除试验，将副本从原语料缩减到 31 行，保存为 `baseline-reduced.lua`。这只是预算内、按行删除得到的局部缩减，不声称全局最小。缩减版的错误第二返回值可成为 table 引用，进一步提示是数据/状态映射问题，但根因未确定。

完整输出差异、产物哈希、每次运行情况见 `baseline-discrepancy.json`。原始源文件和引擎均未改动，历史固定矩阵全绿的事实也未改写；扩展随机测试补上了一个新覆盖面。

**后续若要实现新机制，应先单独处理这个基线问题，再比较候选；否则可能把旧 bug 错怪给新机制，或将新检查触发误当成安全收益。** 本轮遵守“只研究”，没有修复。
**根因追加（2026-10-09）：已定位并实证——v15 全展开调用的动态结果窗口未被保留，H3-4 死寄存器噪声覆盖返回值；消融实验 8/8 修复、健康种子不受影响。见 [`root-cause/ROOT-CAUSE.md`](root-cause/ROOT-CAUSE.md)。修复待批准，生产代码未动。**

## 8. 五小时长跑究竟做什么

运行脚本：

```bash
python3 -u research/antidebug-20261009/sweep.py \
  --seconds 18000 --seed 2026100905 --prefix extended
```

39 个可信源码（37 个现有语料 + R064 + R066），先逐个覆盖，再随机选源码和非零 64-bit seed。每组做：

1. 现役引擎生成；
2. Luau 编译；
3. 原产物与源码 stdout/退出码比较；
4. 同一产物的无凭证外层 adapter 与带凭证外层 adapter 比较；交错 A/B 执行顺序；
5. 记录生成大小/时间、外层 CPU 时间；逐条刷新 CSV；定期复核 353 个原文件。

**第 4 项只覆盖根调用一次，不是每个 VM 内部调用都加了凭证。** 根调用额外成本很小，不能用它近似每指令/每调用的微基准代价，更不能代表整体保护已验证。

超时、编译失败、基线差异、adapter 差异分开记录；不把 124 超时算作成功；不通过 sleep 消耗预算。最多保留 25 个失败样本目录，位于被忽略的 `work/`。每条 CSV 可以用源码路径和 seed 重建，避免保存大批产物。

只有 `extended-status.json` 状态为 `completed-time-budget` 才表示达到时间预算；`running` 是仍在运行，`stopped`/沙箱重置是未完成。新 case 在时间预算截止前停止接纳，当前 case 仍可能花最多数个子进程超时窗口收尾。

本地时间是沙箱时钟；本报告使用任务日期和单调时钟耗时，不据此捏造五小时已经过去。长跑结果也不等于五小时持续人工分析。

## 9. 下一步研究优先级（不授权实施）

1. **先建立稳定基线**：独立定位上述语义差异；当前只记录，需用户另行批准修复。
2. **C1-internal 继续设计**：仅复用现有分散 CALL/POSTCALL 边界，不增加 wrapper/中央 registry；定义错误/yield/cancel/重入生命周期。必须承认只读观察与完整回滚仍能绕过。
3. **C2 谨慎推进**：先证明不会额外暴露全 CFG，也不会重复分支谓词/用户代码；不能拿线性校验充当认证。
4. **C3/C4 朴素方案不加入**：已有明确语义/安全/性能反例。
5. 真正的入选门槛还包括：正式内部原型开关关闭时字节一致、全语料多 seed、原有 loader/窗口/descriptor/分散化审计不退、攻击成本对照、真实目标环境验证与成本预算。本轮没做内部集成，故这些门槛**尚未完成**。

**有限测试无法证明对所有攻击者和运行环境“绝不倒退”。能做的是把威胁模型写清楚，保留原有防线，以对照实验和反例不断收窄风险；不达标就不加入。**
