# 前台第二轮：CALL 边界内联校验的可行性与反例

**日期：2026-10-09。范围：继续前台研究；原五小时后台任务未停止、未重启。**

## 本轮结论

前一轮把新校验套在函数外面，会改变调用栈；本轮改为在**独立模型的同一调用边界内部**插入检查，确认可以避开其中一部分兼容性问题。

但这不等于已经获得新的强反调试层。准确的功能描述应降级为：

> **某个调用期间，检测选定帧元数据的持续改变。**

它无法凭自身证明原函数真正执行、参数和结果正确，不能检测只读观察，也不能覆盖完整状态回滚。当前仍然**不达到上线门槛**，现役引擎没有加入任何东西。

机器可读证据：[round2-evidence.json](round2-evidence.json)。所有原有 353 个文件复核未变。

## 1. 先把实际 CALL 生命周期弄清楚

从 `obsucvim/src/vmgen/template.rs` 只读核对：

1. `M_CALL / M_CALLE / M_CALLM / M_CALLT` 填充家族自己的稀疏参数槽，设置 `E.callx`。
2. 蹦床根据 `(E.callx - E.vd) % 17` 选择原有四个浅层 executor 之一。
3. **蹦床先把 `E.callx` 置 nil，再调用 `cx(E)`。**
4. `CX` 执行 `E.tp(fn(E[21](args, 1, nargs)))`，得到带精确 `.n` 的返回包。
5. POSTCALL 按调用家族安放结果。
6. 清理该家族逻辑槽 `0..8`。
7. 执行 `chain_epilogue`：继续取指、推进 PC，可能准备好**下一次** CALL，之后才回到外层蹦床。

这说明不能笼统地说“调用前记一下、`cx(E)` 返回后再检查一下”。后面的 `E` 可能已经属于下一个合法阶段。

### 顺序模型复现

`boundary_order.luau` 得到 1 个正向检查和 3 个反例：

- 整个 CX 返回后比较原 PC/原凭证，会把已准备的下一次合法 CALL 当成篡改。
- 整个 CX 返回后再清理旧凭证，可能擦掉下一次 CALL 的凭证。
- 要求 CX 入口的 `E.callx` 仍等于 CALL producer 写下的值也错误，因为蹦床早已主动清空它。
- 在本模型内，**用户调用返回后、POSTCALL/后续尾链之前**完成当前凭证消费，才不覆盖下一个 generation。

这是从现有代码顺序导出的工程约束，不是把三种错误设计加入过实际 VM 后测出来的结论。

## 2. 同边界内联模型：哪些兼容性问题得到缓解

`inline_interval.luau` 的模式开关只控制校验语句，不在模型 boundary 和用户回调之间增加 wrapper 或 `pcall`。测试覆盖：

- 同一 boundary 的调用者身份和调用位置；
- `error(..., 2)` 的同一 callsite 错误位置；
- 5 个实参/返回值中的前、中、尾 nil；零返回；nil 错误和 table 错误对象身份；
- 合法 table/upvalue 修改、受保护 `__call`、64 层递归；
- 32 个协程交错、共 640 次 yield/resume；
- ticket、sequence、phase、function reference、参数表引用、arity、PC、family 八种单字段持续篡改；
- raw identity 比较不触发用户 `__eq`。

结果：**19 项正向检查通过，7 项局限/副作用反例复现。**

### 必须保留的限定

A/B 都调用同一个研究函数中的同一行。这个实验说明“额外 wrapper 不是必须的”，**不证明把新语句发射到现役 VM 后源行号、局部寄存器数、短名分配、递归极限等一定不变**。本轮未进行正式 VM 内部集成，也未声称完成这些门槛。

## 3. 在内联之后仍然存在的绕过

### 3.1 预先篡改

如果校验器进入时，函数引用已经被替换，它从被替换的帧里取“期望函数”，自然会接受替换后的行为。运行前数据校验与运行期间数据不变性不是同一件事。

### 3.2 观察后恢复

记录参数/函数引用、临时修改 PC、再把 PC 恢复：所有结束时比较都通过。两端快照相等无法证明中间没有被观察或改过。

### 3.3 不检测参数表内容和任意返回值

为避免复制明文/触发用户元方法，本模型只检查参数容器身份和 arity，不检查所有元素和可达用户对象。容器身份没变，不代表容器内容没有被写过。

也不能对任意用户返回值预知正确答案。校验器正常结束，不代表返回的数值或对象来自原语义。

### 3.4 抛错和取消路径

不额外加保护调用时，抛错会直接越过后置检查；协程取消同样不会执行正常返回后的清理。

**这不等于现役 VM 已有内存泄漏。** 本实验为了观测结果持有 E 的外部引用；实际无外部引用的废弃帧可以由 GC 回收。真正的约束是：不能为了补清理而新增强引用全局注册表，不能假定后置检查覆盖所有退出路径。

### 3.5 不是“调用真的执行”的证明

`completion_forgery.luau` 专门构造两个反例：

- 保留所有 ticket/phase/seq 的正常推进，只跳过实际用户调用并填入假返回包；全部校验通过，用户函数的副作用计数未增加。
- 用户函数正常调用后替换返回包的值，同时保持 `.n`；全部校验通过。

有 1 个正常对照和 2 个反例。这是合成调用模型中的故障注入，不是实际产物破解工具，不外推攻击者能用同样代码直接修改正式混淆产物。

**因此不能把“令牌消费成功”称作“计算真实性认证”。**

## 4. 原语依赖不能被模型偷偷理想化

首个内联模型使用外层捕获的 `PACK/UNPACK`；现有 CX 的实际形式则通过帧引用 `E.tp / E[21]` 访问相应原语。因此又单独做了 `primitive_contract.luau`：

- 替换模型中的 pack 引用，可以在原函数确实执行后产生伪造返回值。
- 替换 unpack 引用，可以传入与参数表内容不同的实参；参数表身份和 arity 检查仍通过。
- Lua 会先解析外层调用 `E.tp` 的函数值，再计算它的参数。所以用户回调期间改变 `E.tp`，可能不影响这一次，但会影响下一次调用。

结果：2 个正向检查、3 个反例。

这些反例说明**候选校验覆盖的字段不完整**；它们不构成“现役引擎已能被普通用户脚本直接访问 E 并替换 pack/unpack”的证据。实验明确给予了模型攻击者 E 访问能力。现役已有原语捕获/环境校验不能因此被删除或替代。

## 5. 对象凭证与数值 generation 的代价/安全交换

为减少每次调用新建 ticket table 的开销，比较了：

- 模式 0：共同的无校验模型；
- 模式 1：仅数值 generation、phase、引用/PC/family 不变性；
- 模式 2：模式 1 加新对象 ticket 身份。

每组 80,000 次调用，12 轮轮换测量顺序。保留两种写法的结果，避免只挑有利的一组：

| 研究模型写法 | 数值版/基线 中位比 | 对象版/基线 中位比 |
|---|---:|---:|
| 正常路径用 `assert` 表达检查 | 1.910× | 2.204× |
| 失败才进入 `error` 分支 | 1.758× | 2.027× |

另一个内联模型 9 轮中位比为 1.939×，不要与不同代码形态的表格机械合并。

**限制：**这是极短函数的微基准；A/B 的共同函数甚至保留了一些相同元数据读取。它既不是完整 VM 开销，也不是可达到的性能下界。后台 seed sweep 同时运行，没有独占 CPU；全部样本见 JSON，未宣称统计显著性或固定倍数。

### 数值版的 ABA 风险

16-bit generation 在再经过 65,536 次调用后会重复，保留的旧序号可与当前序号相等；旧对象 ticket 与新对象 ticket 在旧引用仍被保留时不相等。

把 generation 改为“不取模一直 +1”也不是无限计数：Luau double 到 `2^53` 后加 1 不再推进。更宽的有界精确计数可以延后问题，但仍不能解决全状态回滚。

这不是说对象 ticket 对完整观察者保密，也不是说所有数值协议都不可用。它说明：**为了省一次对象分配，不能把两种机制当作安全性质等价。**

## 6. 新字段是否会撞现有帧槽：单独做布局枚举

`slot_audit.py` 先核对当前源文件的公式锚点，再枚举：

- `vd % 4096` 的 4,096 个值；
- 当前 stride 的 1..16，共 16 个值；
- 合计 **65,536 个布局组合**。

在所检查的数字字段范围内，四个 call-family 各从逻辑槽 `0..8` 扩到 `0..12`，未与现有 core/return 页或其他 call-family 槽相撞。

但有三个不能忽略的结果：

1. 当前清理循环只清 `0..8`。若追加 9..12 又不改清理，它们会被留下。
2. 不能任意往后加：stride=16 时，family 1 的 logical 16 与 family 2 的 logical 0 重合；其他更远组合也有碰撞。
3. 数字槽 base 不能当帧身份：例如 `vd=1` 和 `vd=4097` 得到相同 base。同原型递归调用也会复用布局，但由不同 E 表隔离。

**这只是被核对公式的命名空间检查，不是所有发射字段的完整静态验证，更不是已加字段后的运行测试。** 本轮没有向现役 E 增加任何字段。

## 7. 到这里，候选应如何收窄

如果以后另获授权做内部原型，应先写出以下契约，而不是先把代码塞进去：

- **保护对象**：只选择 VM 私有控制元数据；不能把用户可合法修改的表/upvalue 当作必须恒定的数据。
- **信任来源**：期望值何时、从哪里产生；如果与观测值都来自同一个已被修改的帧，就不能叫认证。
- **消费点**：在调用返回后的正确内部边界消费，早于当前 POSTCALL 尾链准备新调用；不能在整个 CX 返回后统一清旧状态。
- **异常与取消**：明确未执行后置检查的路径，不能为了“补齐覆盖”破坏现有 pcall/错误对象/协程行为。
- **状态布局**：新增字段与分散清理规则同步设计，不引入全局可枚举 registry。
- **无回退的实证**：原有防线不删、关闭路径字节一致、旧明文窗口不扩大、语义/攻击/性能对照及真目标环境验证。上述尚未完成。
- **宣传边界**：最多声称某类持续元数据篡改的检测；不能声称检测到一切调试器、阻止语义观察或验证全部返回值。

本轮获得的是更准确的范围和反例，不是批准一个新防护层上线。
