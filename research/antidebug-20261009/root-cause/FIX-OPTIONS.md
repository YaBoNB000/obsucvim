# 三条修复路线详解（研究文档，未实施）

> 前置事实（决定三条路线的可行性边界）：
> ① 编译器在每个调用点**知道**结果数 `nres`：`local a,b = f()` → nres=2；`for ... in f()` → 3；单值上下文 → 1。这些**有界窗口**尺寸编译期已知。
> ② 出问题的只是**动态窗口**（`c=255` / CallE / CallM 动态计数）：`return f(...)` 尾调用、`g(f(...))` 展开实参、变参转发 `f1(...)`。返回数量运行期才知道，**理论上无上界**。
> ③ `CallT`（表构造器尾调用）结果直接进表，不落寄存器——不受此 bug 影响。
> ④ 现役 Call handler 已有 `if s then V[s]=… else O[base+i]=…` 的 X 溢出路径，说明设计者已知窗口可超出 S 表——但溢出目标 O 同样可能被噪声写碰撞。

## 路线 1：编译期保留结果窗口

**原理**：全展开调用的结果窗口 `[base+1, base+nout]` 在编译期显式 `reserve()`，让死寄存器基址（`dead_base = nregs`）抬到窗口之上，噪声就不可能落在窗口里。

**具体改动**（`compiler.rs`）：
- 四个有界调用点（nres=1/2/3/目标数）补 `reserve(nres)`，确认结果落位与目标寄存器/临时寄存器不越界。这部分是低风险加固——固定矩阵一直绿，说明现状大体正确，但没有静态不变量保证。
- **动态调用点无法照做**：`f1(...)` 转发的 nout = 运行期 vargc，`return f(...)` 的 nout = 被调函数实际返回数。编译期"保留"只能选一个上限 K：
  - K 太小：返回值 > K 时窗口再次越界，**同类 bug 只是变得更稀有**；
  - 想保正确就必须加"超 K 溢出到别处"的协议——那实质上就变成了路线 3。

**结论**：路线 1 单独**不是完整修复**。它的真实价值是有界窗口的加固 + 把"寄存器谁在用"显式化，应作为路线 2/3 的附带项，不宜单独作为修复宣称。

## 路线 2：噪声避让（H3-4 注入器感知活跃窗口）

**原理**：窗口照旧动态，但让 H3-4 注入器在选 (位置, 死寄存器) 时避开"打开中的动态窗口"。

**具体改动**：
1. `finish()` 里噪声注入前，对最终指令序列做一趟扫描，构建禁止区间表：
   - 触发指令：`Call(c=255)`、`CallE`、`CallM(c=255)`（结果数动态的调用家族）；
   - 窗口：从该指令起，**logical 寄存器 > base 的全部**（因 nout 无上界，只能按开区间到 ∞ 处理），直到消费者指令（下一个 Call 家族或 Return，保守取先到者）；
   - 死寄存器 dst（`dead_base + k`）落进当时打开的窗口 ⇒ 该 (位置, dst) 禁用，Nop 不受限。
2. 用"先过滤候选池再抽取"的方式实现，避免重试循环扰动 RNG 日程（日程变了也要如实记录，同 seed 产物必然变化）。
3. **配套加一条构建期静态不变量**（这是本路线的精华）：注入完成后断言"不存在任何指令写进打开中的动态窗口"——把这次事故变成机器可查的不变量，未来任何新 pass 违反会直接构建失败。

**代价与风险**：
- 转发型小函数（base 很低）里窗口覆盖几乎所有死寄存器 ⇒ 这些函数的**活性噪声变少**（只剩 Nop）。这是防护面貌的小削弱，需同步检查 `h3_noise_audit.py` 的统计预期；不能瞒着不报。
- 窗口模型本身可能漏消费者形态（如某处晚于模型关闭点才读窗口）⇒ 残余风险。缓解：保守关闭点 + 大规模随机 seed 回归。
- 改动半径最小（一个函数内），不动调用 ABI、不动 micro recipes、不动既有审计语义。

## 路线 3：全展开结果改走帧槽（结构性根除）

**原理**：动态结果不再落寄存器堆。CX 拿到的打包表 `E.tp(fn(...))` 本来就带精确 `.n`——现在它被 POSTCALL 拆散进 V，消费端再从 V 读回。改为：**打包表直接存进返回页帧槽**（`E.rb` 页，现有 lastbase/lastn/out/total 旁加 1–2 个槽），消费端直接读表。

**消费端逐个改**：
- `Return 255` 合并：`out[pre+j] = 结果表[j]`，替代 `V[S[lastbase+j]]` 回读——**少一次散开再收拢，可能还更快**；
- CallE/CallM 外层读内层展开结果：`av[off+j] = 结果表[j]`，替代 `V[S[z]] or X[z]`；嵌套 `g(f(h(...)))` 中每层"先读完内层窗口、再写自己窗口"，单槽时序上成立，但这正是最容易埋 seed 相关 bug 的地方（R064 的教训）；
- X 溢出路径整体退役（打包表天然无寄存器上限）；
- lastbase 帧槽随之退役或降级。

**代价与风险**：
- 改动半径最大：M_CALL/M_CALLE/M_CALLM/M_RETURN 的 micro recipe、POST_CALL 家族、H4-7 call 页布局、micro fusion 单测、h8 投毒审计、r064 seed 稳定性回归都要同步。帧页需扩 1–2 个逻辑槽（此前槽位审计已确认 rb 页有余量，但需重跑扩页后的碰撞枚举）。
- 全部 v15 产物字节变化（三条路线皆然，但 3 变化最深）；R065/R066 等存档靶标需按仓库惯例重生成并记录新旧哈希。
- 好处是**整类问题永久消失**：任何 logical > base 的寄存器都不再被动态写入，路线 1 的"无上界"困境和路线 2 的"窗口模型可能漏"都不存在了；不变量"寄存器堆只被编译期已知索引写入"可以静态成立。

## 对比与建议

| | 1 保留窗口 | 2 噪声避让 | 3 结果走帧槽 |
|---|---|---|---|
| 根治程度 | 部分（有界可修，无界不行） | 高（护住已知写入者）| **整类根除** |
| 改动半径 | 小 | 小（单函数+新不变量） | 大（调用 ABI） |
| 残余风险 | 无界场景仍在 | 窗口模型漏形态 | 实现期时序 bug |
| 性能 | 无影响 | 无影响 | 中性偏正 |
| 活性噪声 | 不减 | 小函数减少 | 不减 |

**建议分两步走**：
1. **先做路线 2 + 构建期不变量**（最小止血，附带路线 1 的有界加固）：把 9 个已知失败 seed 固化进 `r064_seed_stability_test.sh` 式回归，再跑一次此前中断的随机 seed 长跑验证全绿。
2. **再立独立增量做路线 3**（真正根除），走完整强制工作流：cargo test + 169/370 矩阵 + multiseed（含扩展随机 sweep）+ H 系列/D 系列/S1–S5 审计 + 示例与存档靶标重生成 + 四处文档同步 + 提交推送。

三条路线都会改变同 seed 产物字节（这是修 bug，不是无影响开关）；0.7% 的触发率意味着验证必须靠大规模随机 seed，不能只靠固定矩阵——这正是本次事故的教训。
