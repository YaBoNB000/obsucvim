# LZ/Gzip 运行时解包研究（安全约束版）

**日期：2026-10-21**  
**目标**：探索 LZ/gzip 能否在不形成新漏洞、且不明显降低混淆强度的前提下，将 v15 产物压到 200KB。  
**边界**：纯研究；正式 `obsucvim/src` 零修改。开工 SHA-256 清单 `baseline-sha256.json`（154 项），研究结束复核仍为 154/154 一致。

## 先给结论

**不建议把整个混淆产物 gzip/LZ 后在启动时解压成 Lua 源码再 `loadstring` 执行。** 这种做法理论上能把 212,137B 压到约 66,503B，但运行时必须先把完整、可读的 VM 源码复原，再交给动态 loader。攻击者只需在第一条保护逻辑运行前 hook `loadstring`，就能直接截获整份解压源码；这会新增一个比当前 D9 反挂钩更早、更集中的 oracle。压缩不等于加密，且这里会削弱保护边界，拒绝。

本轮最安全、最有实际收益的发现是**随机种子候选择小**：保留同一套变换和五项运行时保护，只在用户未指定 seed 时，对极小源码尝试若干独立随机 seed，选产物最小的一份。它不加解压器、不删保护层、不改变 VM/加密/运行逻辑；seed 仍写入产物，用户可用选中的 seed 复现。R067 canary 的 16 候选实验中，16/16 组均得到 <200KB 产物。**这是候选方案，尚未接入产品**；best-of-N 对随机布局有尺寸偏置，需要单独评审/验收。

## 实测基线

全保护（v15 + VM 字符串封存 + env-check + executor binding + Roblox env binding），使用研究基线二进制：

| 输入 | 输入字节 | 基线产物 | gzip 对照（仅压缩文件，不是可运行 `.lua`） |
|---|---:|---:|---:|
| R067 `print("suda")` | 14 | 212,137B | 66,503B（-68.7%） |
| DEMO 游戏模块 | 2,177 | 290,313B | 91,915B（-68.3%） |

产物已由默认 `--minify` 输出。再运行一个 Rust 感知、保 token 序列的空白压缩器：

- R067：212,137 → 212,136B（**只省 1B**）
- DEMO：290,313 → 290,312B（**只省 1B**）

结论：单纯压 whitespace 已无空间。

## 路线 A：整份 Lua 源码 LZ/Gzip → 解包 → `loadstring` 执行

- **体积收益**：极高，gzip 约压到原体积 31%。
- **安全结果**：拒绝。
- **原因**：必然出现“解压明文 → 动态 loader”边界；在解压后的代码第一条自检运行前，hook `loadstring` 就能记录完整明文。即使随后 D9 检测并杀死当前执行，也不能收回已被截走的源码。若改为把解压出来的整段源码 `print`/传给回调，问题更直接。
- **结论**：不做产品原型、不做默认实现。最多可用于外层下载包/分发压缩文件；不能把压缩后的包装器误称为更强混淆。

## 路线 B：压缩 VM proto/字节码块，再走现有加密与 VM parser

这是较安全的 LZ 集成点：**先压缩结构化 VM proto bytes，再用现有每函数 stream mask 加密；运行期在 VM 内部解密后，将解压字节直接交给现有 section parser**。这样压缩数据仍加密驻留，不重建整段 Lua 源码、不新增 `loadstring`/source oracle。若继续研究，必须带：原始长度上限、压缩标志认证、严格的窗口/输出长度界限、畸形流 fail-closed、在现有 hash/poison 校验后解压，并对合法输出逐字节等价。

但当前 proto 数据可压缩量太小：本轮在**研究副本**中于序列化后/加密前转储了 proto blobs，作 zlib-9 上界测量（zlib 比定制 LZSS 更重，已给压缩器较宽松的上界）：

| 样本 | proto 原始总量 | zlib-9 后 | 节省 | 对整产物的意义 |
|---|---:|---:|---:|---|
| R067 14B | 137B | 148B | **-11B（反而增长）** | 无收益，应跳过小块 |
| DEMO 2.2KB | 4,857B | 4,688B | 169B（3.5%） | 整产物只省约 0.06% |
| R064 7.2KB | 15,710B | 14,317B | 1,393B（8.9%） | 340,895B 产物最多省约 0.4% |

**判定**：方向安全性上可行，但目前字节收益不足以支付 LZ 解码器、格式版本、畸形输入防护与回归维护成本。R067 的 200KB 目标也帮不上忙（几乎零字节）。**不建议现阶段实现。**

## 路线 C：VM 字符串封存关闭（对照，不作为推荐压缩）

`--no-vm-seal-strings` 是已有真实 CLI 选项，保留 L2 字符串处理，但关闭 VM 编译前的独立封存层。固定 seed 示例曾看到显著下降，因而对 20 个随机 seed 做配对，结果显示高度不稳定：

| 样本 | seal ON 平均 | seal OFF 平均 | OFF 相对 ON 平均节省 | 配对差值范围 |
|---|---:|---:|---:|---:|
| R067 14B | 213,555B | 213,329B | 226B | -35,472…+39,610B |
| DEMO 2.2KB | 265,941B | 271,472B | **-5,531B（平均更大）** | -38,160…+43,552B |

OFF 的 demo 固定样本中，源码标记仍 0 命中、S1–S5 仍 5/5、37 个语料语义 37/37；但这明确移除一层独立封存，且尺寸变化主要由 seed/布局耦合驱动。**不建议静默关闭或默认切换**；只保留为用户现有的显式自定义项。

## 路线 D：缩短 obf_num 算术表达式（研究副本）

实验把三项 `x+y-z` 改成两项 `x-y`：功能测试 222/222、S1–S5 5/5、D2 三个 seed 全过；然而尺寸极不稳定：

| 样本 | 固定 seed | 20-seed 平均节省 | 配对差值范围 |
|---|---:|---:|---:|
| R067 14B | 435B | **-2,597B（平均更大）** | -39,088…+21,292B |
| DEMO 2.2KB | 24,958B | 2,262B | -43,050…+36,989B |

改变会减少数值遮蔽表达式的一项，且小脚本节省近零/平均可能膨胀。**不满足“稳定压缩且强度不降”的标准，拒绝纳入。**

## 路线 E：best-of-16 随机 seed 择小（推荐候选，未实施）

保持混淆算法、保护开关、产物格式完全不变；只在 seed 留空且输入极小（研究建议 ≤256B）时，从独立随机 seed 生成最多 16 个候选产物，选最小者。显式 seed 请求完全不变。源代码/保护层不删、不加解压器；最终 seed 正常记录，可单独复现。

R067 14B 样本测量：

- 328 个随机 seed 单次构建：**32.0%** 产物 <200,000B。
- 8 组顺序池 + 8 组密码学随机池，共 **16 个 best-of-16 池：16/16** 最小产物 <200KB，尺寸 **192,081–194,045B**。
- 加密随机池胜出产物全部 luau-compile 通过；4 个样本 S1–S5 **5/5**、D3 **22/32**（等于当前优化基线）；胜出 seed 在 DEMO 上语义 8/8。
- 单次小脚本 CLI 约 0.12s；16 次预计约 2s（仍需在真实 web API 计时/限流下验证）。

**安全边界**：没有减少任何一层，安全指纹/结构指纹抽测没有下降；不过 best-of-size 会偏向更短的随机布局，这种选择偏置尚未经过独立攻击方的深测。16/16 是样本结果，不是任意输入的硬保证；大脚本也未证明能压到 200KB。

## 推荐决策

- 若目标是：**用户留空 seed 的极小脚本尽量低于 200KB，且不删保护层**，先实现路线 E 为实验开关（只对空 seed + ≤256B），给最大候选数/时间预算；对照测试报告两种 seed 行为。
- 若目标是：**所有脚本都保证 <200KB**，本轮没有安全合格的通用源码压缩法。整源 LZ+loader 被拒；proto LZ 的数据量上界太小；要达到显著压缩只能做 VM/模板架构级去重，并重新评估结构可逆性与 D1-D18。
- 正式生产源码 SHA：154/154 不变；本报告及实验副本均在 `research/size-compression-20261021/`，未修改 `obsucvim/src`。
